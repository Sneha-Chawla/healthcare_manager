# System Design Write-up

The system is designed around the idea that healthcare booking is a consistency problem first and a form-submission problem second. Patients, doctors, and admins use separate role-based portals, but all critical operations pass through the backend API so authorization, slot validation, notifications, and audit records stay centralized.

Double-booking is prevented with a database transaction and a dedicated `BookingLock` table. When a patient confirms an appointment, the backend validates doctor working hours, leave days, and temporary slot holds. Inside the same transaction, it inserts a booking lock with a unique constraint on `doctorId + startAt + endAt`. If two patients try to book the same slot at the same time, the database accepts only one insert and rejects the other. This is safer than checking availability only in application memory because it works even when the backend runs on multiple servers.

The slot hold mechanism improves user experience during checkout. When a patient selects a slot, the API can create a short-lived `SlotHold` record, usually valid for five minutes. Other users do not see that slot as available while the hold is active. If the patient does not confirm in time, a background job expires the hold and the slot becomes available again. Confirmation still uses the final booking lock, so even expired or duplicated holds cannot create double-bookings.

Doctor leave management is handled as a workflow, not just a database update. When an admin marks a doctor on leave, the service checks existing appointments for that date. Future appointments are marked as `CANCELLED_BY_CLINIC`, calendar events are deleted or updated, and affected patients receive email notifications. A notification record is stored for each patient so failed sends can be retried. This makes the system reliable even if the email provider is temporarily down.

LLM integration is intentionally non-blocking. Before a visit, the patient submits symptoms and the LLM generates urgency level, chief complaint, and suggested questions for the doctor. After a visit, the doctor submits notes and prescription details, and the LLM converts them into a patient-friendly summary. If the LLM provider fails or times out, the appointment still succeeds. The system stores a safe fallback summary with `llmStatus = FALLBACK`, allowing the doctor to continue work while preserving visibility into what happened.

Notification reliability is handled through persisted records and background jobs. Booking confirmations, reminders, cancellations, medication reminders, and email retries are queued. Each notification has status, retry count, and last error fields. The worker retries transient failures with backoff instead of losing messages. Calendar events use the same principle: the appointment is the source of truth, and calendar sync can be retried or repaired later.

The database schema separates users, doctor profiles, appointments, symptoms, LLM summaries, prescriptions, notifications, calendar events, slot holds, booking locks, and leave days. This keeps the model explainable and supports future growth such as multiple clinics, payment, lab reports, or telemedicine links.
